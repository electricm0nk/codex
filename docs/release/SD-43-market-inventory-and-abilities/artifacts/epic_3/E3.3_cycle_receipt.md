- **Rulings and defaults applied:** `technical-design.md` §3.2 (Traits keep `selected_traits`). Defaults taken (§30, no operator question):
  (1) a trait with a skill choice is added through the existing `add_trait_selection` command (records the skill in `selected_choices`)
  because E3.2's generic `add_ability_selection` records no choice (E3.2 Does-not-cover 4); every other pick goes through
  `add_ability_selection`, whose refusals are the engine's; the alternative (generic add, then a second call for the choice) would leave a
  held trait with no skill when the second call fails. (2) The Qualified filter starts off, so unqualified options show, drawn italic,
  struck and faint (PCGen draws them in red). (3) The Info pane's prose and grants line come from the trait roster
  (`list_available_character_traits`); for a trait the roster does not carry, it prints one sentence saying so.
- **Does not cover:** (1) The choice path's budget gate is the UI's (Add disabled from the engine's `qualified` / remaining row), not a
  server refusal: `add_trait_selection` checks only "already held" and a valid skill; a caller bypassing the UI could exceed the pool with a
  choice trait. The choice-trait population is the roster's `choiceSetId` options (`SKILL_CHOICE_TRAIT_BONUSES` + family-choice table in
  `src/rules_core/trait_effects.rs`; not counted here). Closing it needs a choice parameter on `add_ability_selection` (Rust, outside this
  card's no-cargo scope) — E3.4 is the generic add's next writer. (2) Selected shows a choice trait's grants line ("+1 to a chosen skill"), not
  which skill was chosen: the load response does not carry `selected_choices` for traits (`traitsTabModel.ts` documents the same gap).
  (3) Prose exists only for roster traits; the engine lists every trait principal (E3.2: 476 distinct slugs, its Python walk), most without
  prose in the Info pane. (4) The view test renders with `renderToStaticMarkup`; the stateful loader (`AbilitySubTab`: fetch, refetch on held

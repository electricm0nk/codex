# Tranche-2 Install and Use Matrix

## Purpose
Define the current-truth install/use authority surface for tranche-2 tester builds so acquisition, install prerequisites, launch path, bounded workflow entry, failure evidence, and status posture are explicit per tester-support path instead of implied by authoring-machine folklore.

## Boundary of this surface
- This matrix is a current-truth documentary surface, not a clean-machine receipt and not proof that any row already passed.
- This matrix inherits channel/support posture and distribution truth from SD-12, bounded workflow truth from the current repo/program status surfaces, and failure-evidence requirements from the SD-15 regression receipt schema.
- No row below claims clean-machine success, external-test completion, updater parity, rollback execution success, or tranche closure.
- When a path is not grounded by live authority surfaces, the row remains `blocked`, `unsupported`, or `out-of-scope` rather than guessed into a fake `pass`.

## Status vocabulary
- `not-run` — the path is sufficiently grounded to attempt, but no run evidence is attached yet
- `pass` — the named step/path completed and the required evidence exists
- `pass-with-known-bounds` — the path completed with an explicit limitation that does not counterfeit broader support or closure
- `blocked` — a prerequisite, governed artifact handle, environment fact, or proof surface is missing badly enough that the path cannot yet be judged honestly
- `unsupported` — adjacent authority explicitly says the path lies outside accepted support posture
- `out-of-scope` — the path is intentionally excluded from tranche-2 tester install/use proof

## Row population rules
- Do not mark any row `pass` or `pass-with-known-bounds` unless a later run attaches the row's required evidence.
- Use `blocked` when the current live surfaces do not ground the exact artifact, acquisition handle, environment, or launch path well enough to judge the row truthfully.
- Use `unsupported` only when adjacent authority already fixes the path as unsupported or unavailable; do not use it as a synonym for "we have not checked yet."
- Use `out-of-scope` for paths that are intentionally excluded from official tranche-2 tester proof, including reserved channel semantics with no governed backing surface.
- If a row reaches the bounded workflow but fails deeper inside the product, keep the install/use proof honest and re-route the failure to `ui or presentation defect`, `rules-engine defect`, `content or data defect`, or `persistence, migration, or saved-state continuity defect` as the evidence dictates.
- If a row fails because the durable truth surfaces contradict one another, route the result to `status or documentation drift` instead of flattening it into an install/use bug.

## Required failure evidence baseline
Every failing or blocked row should produce or reference an SD-15 receipt containing, at minimum, the fields needed to reconstruct the path:
- `build_label_or_version`
- `tester_channel_support_label`
- `operator_provenance_handle` and `commit_or_build_identity` when available
- `publication_or_acquisition_handle` and `package_install_context` when relevant
- `platform_os`, `platform_architecture` when known, and `environment_kind`
- `bounded_workflow_under_test`
- `primary_sd15_class` and `outcome_state`
- `observed_behavior` and `expected_behavior`
- `reproduction_steps_or_impossibility_note`
- `diagnostics_or_status_evidence`
- `attachment_handles`, `attachment_types`, and `redaction_posture`

## Interpretation notes
- Linux is the only platform whose onboarding/build path is concretely grounded in the current repo truth, but that still does not equal a tranche-2 distributed tester receipt.
- macOS and Windows remain visible in the matrix because SD-12 requires explicit posture even when execution proof is absent.
- Automatic update, rollback execution, and withdrawal handling remain adjacent SD-12 authority. This matrix may reference those surfaces, but it does not replace them with parallel semantics.
- A later clean-machine or external-test lane may convert a `blocked` or `not-run` row into `pass`, `pass-with-known-bounds`, `unsupported`, or `blocked` only by attaching real evidence, not by citing this planning text back at itself.
- Repo/program/ledger reconciliation remains a later SD-15 authority surface. This matrix may expose contradictions, but it does not adjudicate tranche closure by itself.

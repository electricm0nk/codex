## What the flow is

New Character under Starfinder 1e opens `StarfinderCreateForm`. Every list and number on it is `preview_starfinder_character`'s answer for the current choices:

| Step | Source |
|---|---|
| race (76 of 77 race records offered: the one without a racial Hit Points row is `core:race:drone`; `python3 -c` over `data/starfinder-1e/sheet_rules/*/race/*.json` counting files with a `"target": "Hp"` rule → `76 77`; `grep -l '"target":"Hp"' */race/*.json \| awk 'END{print NR}'` → `76`) | race records carrying a racial Hit Points row — the row `sf_chassis` refuses a race without; name = the race's `Race`-category ability label |
| theme | `theme`-pool principals tagged `Theme Selection` |
| class + key ability | class principals; `sf_chassis::key_ability_options` (Soldier `STR`/`DEX`, Envoy `CHA`) |
| race/theme/class picks | the held set at 1st level: open `Rules` offers (`offer_open`/`offer_selects`), `Pool(<p>)` rows naming one record (`2_racial_stat_bonus`, held for the player, its choice asked once per pool point), skill/ability value choices; feat pools and language offers are listed "Chosen on the sheet" |
| point buy ("the SF cost table") | `sf_abilities::POINT_BUY_BUDGET` (10), `MAX_SCORE_AT_CREATION` (18) and `sf_abilities::compute` per score with its terms; one point = +1 is the engine's rule (`10 + point_buy` + folded race/theme rows), so the form holds no cost table of its own |

`create_starfinder_character` recomputes the preview, refuses (saves nothing) on any blocking problem, then `sf_adapter::compute_sheet` must succeed before the save. The save is the `CharacterInput` `sf_adapter.rs`'s module table reads: FINAL scores, theme in `selected_feats`, picks as rule choices, the key ability as the class-id choice (and the package's own `Class ~ Soldier` key-ability pick answered from it, not asked twice).

The race count is the package's (two commands above); `race_options` applies the same predicate, and its test asserts membership (the four seed races in, the drone out), not the count.

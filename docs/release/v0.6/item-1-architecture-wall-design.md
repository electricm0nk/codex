# Item 1 — Headless/Corpus-Aware Architecture Wall: Design Pass

> Follow-up to `future-epic-scoping.md`'s gap A. That doc sized this as
> "large, comparable to the Rogue chassis-widening task" from a single
> grep-based estimate. This pass reads the actual call chains involved
> (`pilot_compute.rs`, `pilot_compute_corpus.rs`, `equipment_effects/*.rs`,
> `contract.rs`) and works out concrete numbers, a genuinely new finding
> that changes the sizing, and a recommended fix shape. Design/scoping
> only — no code changes in this pass.

## The headline finding: most of the real math already exists

Before assuming this needs new engineering, I read `equipment_effects.rs`
and its four per-category files end to end. Concretely:

- `compute_equipment_effects(equipped: &[EquipmentSelection], corpus: &SourcePackageContent) -> EquipmentEffects` **already exists, is fully wired, and is corpus-complete** — it resolves every equipment selection, dispatches by category, and returns real AC deltas (`armor_class_delta`), a max-Dex cap, spell-failure chance, and (via `equipmods::compute_equipmods_effect`) a **per-item weapon to-hit/damage enhancement bonus** already read straight off the real corpus `BONUS:WEAPON|...|TYPE=Enhancement` token. This is the function the desktop equipment tab already calls directly for AC — confirmed by the earlier finding in `risks-and-open-questions.md` item 1.
- `pilot_compute_corpus.rs`'s `compute_pilot_with_corpus` (the corpus-aware wrapper every character-mutating Tauri command already calls, alongside the headless call, for `corpus_derived` display data) **already carries a `DerivedEquipmentStats { armor_bonus, attack_bonus, max_dex, spell_failure }` struct on every resolved item** — it has for a while. It is simply never populated (`DerivedEquipmentStats::default()`, unconditionally, at the one call site). The shape for "corpus-aware equipment stats on the receipt" is not a gap; it is dead weight waiting to be filled in.

This means "bridge the corpus wall" is not "build new math" — for AC and the *per-item* piece of attack-bonus, the math is written, tested, and already running in production (via the equipment tab). The actual gaps are narrower and different in kind for each of the three pillars named in `future-epic-scoping.md`:

## Pillar-by-pillar: what's actually missing

### AC
Nothing missing. Already resolved live via the desktop equipment tab calling `compute_equipment_effects` directly. The only "gap" is that the claim-gated `PilotSnapshotDto.baselineArmorClass` (headless-only) doesn't reflect it — already correctly assessed and dropped as a standalone slice earlier this swarm.

### Armor-check-penalty (ACP)
**Much smaller than previously sized.** `arms_armor.rs`'s `compute_arms_armor_effect` already resolves the record's `MAXDEX`/`SPELLFAILURE` tokens by the identical pattern an `ACCHECK` read would use — and its own module doc comment already cites `ACCHECK:0` as a real, present token on the exact record it reads. The gap is a single missing field: `EquipmentStatEffect` has no `armor_check_penalty: Option<i16>` slot, so nothing reads the token into it. This is a same-shaped, few-line addition to a function that already has the record in hand — not a corpus-access problem at all, once inside `compute_equipment_effects`.

### Attack-bonus enhancement
**Real math exists per-item, but there's a genuine data-model gap underneath it, not previously identified.** `compute_equipmods_effect` resolves a weapon enhancement bonus (e.g. "+1 Enhancement to Weapon", a Masterwork/Adamantine/Mithral material) **per equipment-mod item** — but `CharacterInput.chosen.equipment_selections: Vec<EquipmentSelection>` has no concept of one selection modifying another. `EquipmentSelection` is exactly `{item_id, equipped_or_active, active_state}` — flat, no attachment relationship. In real PF1, a "+1 Longsword" is PCGen's own base-weapon-plus-equipmod composition; a player selecting "Longsword" and "+1 Enhancement to Weapon" as two independent equipment selections has no schema-level way to say the enhancement attaches to *that* weapon rather than floating free or attaching to nothing. This is why `compute_equipment_effects`'s aggregate `EquipmentEffects` struct sums `armor_class_delta` (always additive, no attachment needed — armor/shield/deflection bonuses just stack) but has **no equivalent summed `attack_bonus_delta`** — only a per-item `weapon_enhancement_bonus` field that nothing aggregates, because aggregating it without resolving the attachment relationship would be wrong (an enhancement meant for a Dagger would silently also apply to a Longsword attack, or apply twice if two weapons are equipped).

Resolving this needs either (a) a new field on `EquipmentSelection` recording which other selection a modifier attaches to (a real schema change, migration-shaped, touching every file that constructs one), or (b) a narrower convention — e.g. only ever apply a weapon-enhancement bonus when exactly one weapon is equipped, ambiguous/undefined for a two-weapon-fighting build. Neither is a "just thread corpus through" fix; both are genuine design decisions independent of the headless/corpus-aware split.

## The gate is a separate, stricter bottleneck than the corpus wall

This is the most consequential finding of this pass, and it was not stated anywhere in the existing risk tracking: **bridging the corpus wall, by itself, would not let a single additional equipment loadout reach `Computed` today.**

`unmet_combat_posture_conditions` (and `unmet_selected_skill_posture_conditions`) gate on an *exact* `item_id` match — `require_active_state(input, LONGSWORD_ITEM_ID, ActiveState::EquippedActive, ...)`, where `LONGSWORD_ITEM_ID = "item:longsword"` and `CHAIN_SHIRT_ITEM_ID = "item:chain_shirt"` are hardcoded constants pointing at the plain, non-magical base records. This check is entirely independent of whether AC/attack-bonus/ACP math could handle a *different* item — it fails for any item id other than the one literal string, corpus-resolvable or not. Since the currently-`Computed` posture already uses only plain base items, bridging the corpus wall changes **zero currently-displayed numbers** for any build that reaches `Computed` today.

The wall's value is entirely contingent on a second, separate, larger decision this scoping pass surfaces rather than assumes: **would "Computed" ever accept an equipment loadout other than the one exact hardcoded posture?** That is a claim-gating philosophy question (how much variation is "supported enough" to claim correctness) as consequential as the corpus-threading question itself, and nothing in this codebase currently answers it. Fixing AC/attack-bonus/ACP corpus access without also answering this question produces real, tested, unused code paths — accurate math nothing can ever exercise through the claim-gated pillars, because the gate rejects the input before the math would ever run.

## Three fix shapes, compared with real numbers

| | What it does | Real cost | What it actually buys |
|---|---|---|---|
| **(a) Thread corpus through the headless chain** | Give `build_pilot_headless_receipt`/`compute_pilot_base_chassis` a `&SourcePackageContent` parameter, pass it down to `baseline_armor_class`/`compute_combat_baseline`/the skill-modifier functions | Every call site of the two entry points needs a new argument: 19 production call sites (`build_pilot_headless_receipt`) + 37 (`compute_pilot_base_chassis`) + calls spread across 31 test files (not yet counted per-call, likely well over 100 individual call sites given the file count). `pilot_compute.rs` has 59 internal functions taking `&CharacterInput` today; only ~3-4 (the AC/attack-bonus/ACP pillars) would need the new parameter threaded to them, but the *signature* change ripples to every caller regardless of whether that specific call path needs it | Real corpus-aware math reachable from inside the claim-gate itself — but see the gate-independence finding above: buys nothing for currently-reachable builds unless the posture gate is separately widened |
| **(b) Move the `Computed`/`Blocked` decision to the corpus-aware layer** | Derive claim-gating status from `compute_pilot_with_corpus`'s output instead of (or in addition to) the headless receipt's | `CorpusPilotReceipt` currently carries no status/diagnostics field at all — would need a parallel diagnostic-derivation pass mirroring the headless gate's logic, PLUS every Tauri command (`create_character`, `level_up_character`, `add_equipment_selection`, ...) would need its control flow changed from "check the headless receipt's status" to "check the new corpus-aware status." A real, cross-cutting behavioral change to the save/mutate invariant every command currently shares | Same ceiling as (a) — still gated by the exact-item-id posture check unless that's separately widened; also changes what "claim-blocked" means crate-wide, a bigger behavioral surface than (a) |
| **(c) NEW — enrich the corpus-derived DTO section, leave the gate untouched** (this pass's recommendation) | Fill in `DerivedEquipmentStats`/extend `CorpusDerivedDto` by calling the *already-existing* `compute_equipment_effects` from inside `compute_pilot_with_corpus`'s equipment loop (where corpus is already in scope); surface armor-class delta and (once the attachment question is answered) attack-bonus/ACP as an additional, explicitly-not-claim-gated display section, the same way `corpus_derived.equipped_items` already surfaces alongside the claim-gated `snapshot` today | Small-medium: zero changes to `build_pilot_headless_receipt`'s signature or any of its 19+37+100+ call sites; zero changes to claim-gating semantics or any command's save/mutate invariant. Mostly: add `armor_check_penalty` to `EquipmentStatEffect` (few lines, `arms_armor.rs`), call `compute_equipment_effects` once already-corpus-aware, wire the result onto `CorpusDerivedDto`. The attack-bonus attachment question (real design decision, separate from corpus access) still needs answering, but AC and ACP need no such decision — those two are shippable now | Real, accurate, corpus-derived AC and ACP numbers visible to the user for arbitrary gear, in the same additive place `corpus_derived.equipped_items` already lives — genuinely new capability for ACP specifically (AC already has this via the equipment tab's separate direct call), delivered with none of (a)/(b)'s claim-gating risk |

## Recommendation

Shape (c) is the actionable next step if this gets picked up: it is bounded, reuses code that already exists and is already tested, and does not touch the crate's central save/mutate invariant (never persist an unproven build) at all. It closes the ACP gap for real and gives arbitrary-gear AC a second, DTO-native path (redundant with the equipment tab, but consistent). It does **not** close attack-bonus enhancement, which needs the attachment-relationship design decision above resolved first — that's a real, separate piece of scope, smaller than a full corpus-threading migration but not a "few lines" fix either.

Shapes (a) and (b) remain the only way to make the claim-gated `Computed`/`Blocked` pillars themselves corpus-aware — but per the gate-independence finding, neither is worth attempting **until** there's a separate, explicit decision about widening `unmet_combat_posture_conditions`/`unmet_selected_skill_posture_conditions` beyond the one exact hardcoded posture. Recommend surfacing that as its own open question for the operator, distinct from "which fix shape for the corpus wall" — the two are coupled in a way this scoping pass had not previously identified.

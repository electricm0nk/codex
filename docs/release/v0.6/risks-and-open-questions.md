## Risks

1. **Alpha-bar distance — SHARPENED, then SCOPED.** Current state (`docs/architecture/status.md`, 2026-07-23): only single-class Fighter 1–3 reaches a `Computed` receipt; 7 of 10 CharacterSheet tabs stubbed; Feat picker and Money panel do not exist; level-up/skill/bio persistence are no-ops. The §1 bar (6-level multiclass, four books, PCGen parity, zero stubs) requires multiple task waves; the go/no-go checkpoints in §6 are the containment mechanism. **Update (backend, task 2 delivery):** the compute engine's `Computed` path is narrower than "Fighter 1–3" implied — it currently only computes for one exact hardcoded posture. Any other skill/equipment choice returns `Blocked` with diagnostics rather than a receipt — pre-existing engine narrowness, not something the swarm introduced, but it means most tester choices through the newly-wired UI will hit Blocked, not Computed, until this is widened.

   **Full scoping (backend proposal, 2026-07-23, greenlit in part):** the narrowness is actually 4 independent exactness gates in `pilot_compute.rs`, each class-agnostic except one sub-check, any deviation trips `Blocked` with no partial credit:
   1. `unmet_combat_posture_conditions` — exact Longsword+Chain Shirt, no shield, Power Attack selected-inactive, Dodge+Weapon Focus feats (one Fighter-only sub-check).
   2. `unmet_selected_skill_posture_conditions` — exactly Climb/Intimidate/Swim rank 1, chain shirt equipped, nothing else.
   3. A Human-Wizard-only spellbook posture gate (level ≤3, canonical Evocation specialization, exact prepared spellbook) — newly found, wasn't previously documented, fires independently.
   4. AC specifically: `baseline_armor_class` (the gate) never calls `equipment_effects.rs`'s `compute_equipment_effects`, which already computes *real, correct* per-item AC deltas for arbitrary gear and is already wired into the separate desktop-UI equipment tab. The correct math exists and is simply disconnected from the gate.

   **Sizing by pillar (backend's original proposal):** AC — small-medium, a real wiring job (initially greenlit, scoped to Fighter/Wizard/Rogue: splice the existing correct math into the gate). Attack bonus — large, needs genuinely new equipment-driven to-hit math that doesn't exist (feats/enhancement bonuses only today). Skills — medium-large: `allocate_skill_ranks` only maps 5 skills, class-skill recognition is Fighter-only, and has no armor-check-penalty term at all (explicitly deferred in its own doc comment) — not a drop-in fix even for the 5 skills it knows. Wizard spellbook gate — separate, untouched by the above.

   **AC SLICE DROPPED — the real finding is architectural, not per-pillar (backend, mid-implementation, 2026-07-23):** the original AC sizing assumed the correct per-item math could be spliced directly into the gate. It can't, cheaply. `compute_combat_baseline`/`baseline_armor_class` (the thing that gates `Computed`/`Blocked`) lives in the **headless** compute layer — `build_pilot_headless_receipt`/`compute_pilot_base_chassis` take a `CharacterInput` only, **no corpus parameter**, by design. Real per-item AC values only exist via `equipment_effects::arms_armor::compute_arms_armor_effect`, which needs a corpus-resolved `EquipmentRecord` — corpus access the headless layer structurally doesn't have. The static, corpus-free `equipment_tables()` carries no AC-bonus field at all. Bridging this means either (a) threading a corpus parameter through the entire headless chassis call chain — ~347 call-site grep hits, a blast radius comparable to or bigger than task 4's Rogue widening — or (b) moving the `Computed`/`Blocked` decision itself to the corpus-aware layer (`pilot_compute_corpus.rs`'s `compute_pilot_with_corpus`, which already has both), a real architecture decision about which layer owns claim-gating, not an implementation detail. Backend caught this *before* writing the change and stopped to ask rather than push forward on unscoped work or fabricate a corpus-free approximation — correct call, no code written.

   **Decision:** dropped for this swarm. Option 1 (leave the gate alone, since the corpus-aware desktop equipment tab already shows real AC for arbitrary gear today — that's existing behavior, not new work) is close to a no-op and not worth landing on its own. Option 2 (the corpus-threading/layer-ownership change) is a genuine future epic, not a wave-2 item — **flagging for the operator**: this likely isn't just an AC problem. If attack-bonus and general-skill widening (already sized large/medium-large above) hit the same headless/corpus-aware split, bridging that one architecture boundary might be the actual unlock for all three posture-narrowness pillars at once, rather than three independent slices. Worth a dedicated scoping pass before any future wave attempts AC, attack-bonus, or skill-posture widening again. Backend proceeding instead to items 2-4 (durability, money-conversion PCGen verification, comparator field-extraction), none of which share this problem.

   **NEW — Wizard spellbook gate is unreachable, not just narrow (frontend, 2026-07-23).** Gate 3 above turns out to be categorically worse than gates 1/2: it isn't merely one exact combination out of many, it's **structurally impossible to satisfy through any shipped UI path**. `compose_character_input` (the fixed-loadout composer every UI-created character goes through) never seeds the required `choice:wizard_school_specialization -> school:evocation` plus opposed-Necromancy/Transmutation choices for any class, and `CreateCharacterForm.tsx` has no arcane-school field at all. Verified live two independent ways — fresh Wizard creation, and multiclassing Wizard onto an existing character via level-up — both correctly `Blocked` with the real diagnostic, neither persisted (reject-don't-persist invariant held). This directly blocks bar item 3's "select spells at each spell-gaining level" for the entire class most associated with spellcasting, and is likely the deeper reason `status.md`'s "only Fighter reaches Computed" framing has held architecture-wide.

   **Decision:** seed the required choices as a hardcoded default in `compose_character_input`, mirroring the existing precedent — Fighter's loadout already hardcodes Power Attack/Dodge/Weapon Focus the same way, so this is consistent with the fixed-loadout composer's current maturity level, not a new kind of shortcut. Sufficient for the bar: item 3 requires spell *selection*, not arcane-school *choice* — hardcoding the school while leaving real spell selection intact satisfies the literal requirement. A real UI-facing arcane-school selector (frontend's Option A) is a separate, larger feature — **backlog, not blocking**. Backend pausing item 4 to take this first, since it unblocks a literal named bar requirement rather than test infrastructure.

   **SOBERING FOLLOW-UP — Wizard's fix is a lucky exception, not a pattern (frontend survey, 2026-07-23).** Checked the other four caster classes in `pilot_compute.rs` (Cleric, Druid, Bard, Sorcerer) for an equivalent single-seeded-choice gate. None exists. Each has its own `supported_X_level` gate with a doc comment listing genuinely unimplemented calculation subsystems, not missing UI inputs: **Cleric** — no channel energy resolution, no domain spell-list contents, no spellbook posture, no spells prepared, no spontaneous cure/inflict conversion, no spell slots per day, no save DCs, no Wisdom bonus spells. **Druid** — same shape, flat identity records for class features (Wild Empathy etc.) but zero spell math anywhere. **Bard** — flat numbers for non-spell features, explicitly "no spell math whatsoever," plus no bardic-performance execution engine at all (no action economy, no round tracking, no Fascinate resolution). **Sorcerer** — doc comment explicitly says "no bloodline arcana, or spell math," same shape as Bard. None of these are "one missing seeded choice away from Computed" the way Wizard was — they're missing entire arithmetic/mechanic subsystems, which seeding a default cannot fix. **Scoping implication:** the alpha bar's "any class... from the four primary books" (§1 item 2) is a substantially bigger lift than Wizard's fix suggests — backend's incoming fix makes Wizard the *second* class (alongside Fighter) a tester can reach `Computed` with, but the other four full/partial spellcasters remain genuine multi-epic engine work, consistent with `status.md`'s existing "only Fighter reaches Computed" framing. Worth the operator weighing this when judging how close v0.6 alpha actually is to its own bar. **PARTIALLY RESOLVED then CORRECTED, 2026-07-23: the compute-gate fix (3484b5d) landed, but frontend's live testing found it necessary, not sufficient — see the new item 10 below. Wizard does not yet reach `Computed` through any shipped UI path.**

   **Comparator wiring confirms the architecture split is real, not AC-specific — then finds a clean way around it for encumbrance (backend, 2026-07-23).** Wiring `SelectedParityDimensions::from_receipt` to expose the new encumbrance/durability/money PCGen-comparison dimensions turned out to be three genuinely different problems, not one small task — backend stopped before writing code and split them honestly: **(1) durability** — small, bounded, landed. **(2) encumbrance** — initially looked blocked by the exact same headless/corpus-aware wall that killed the AC slice (`compute_encumbrance` needs real corpus-resolved item weights; `from_receipt`'s headless receipt has no corpus access) — independent confirmation the boundary is real. **RESOLVED, not deferred after all**: backend found `contract::PilotReceipt` (produced by `contract::to_pilot_receipt`) is *already* corpus-aware and already carries both `chassis` (the same struct `from_receipt` reads) and a resolved `encumbrance: EncumbranceComputation` — so instead of forcing corpus access into the headless layer, backend added a new, additive `SelectedParityDimensions::from_pilot_receipt(receipt: &contract::PilotReceipt, ...)` that reads from this already-resolved data. `from_receipt` itself is provably untouched (zero blast radius on QA's 3 existing callers). This sidesteps the architecture wall for *parity-testing* purposes without touching the harder problem of moving the `Computed`/`Blocked` gate itself into corpus-awareness (that part of the finding, relevant to AC/attack-bonus/skill-posture widening, still stands as a future epic). **(3) money** — confirmed, not deferred: a different kind of gap entirely, `money.json`'s balance is persisted session state never derived from `CharacterInput`/`PilotReceipt` at all, so there's structurally nothing for any receipt-projection function to expose. **Backlog item stands**: money parity-testing, if ever wanted, needs its own comparison path reading `money.json` directly.

## Open questions

1. **Tranche-6 CI.** No tranche-specific workflow exists past `tranche-3-ci.yml` (none was authored for tranche/5 either). Does `tranche/6` need one, or do `publish-tester-release.yml` + the promotion gates suffice? Owner: operator, pre-launch checklist step 5.
2. **Book-stub label reconciliation.** SD-26's `decisions.md §10` pins the literal `"SD-27"` as the stub resolution bundle while all 21 landed stubs carry `"SD-27+ (unscheduled)"`. Not v0.6-blocking, but the swarm's content work touches `data/stubs/` — the operator should say which label wins before anyone "fixes" it in passing.
3. **Alpha-bar staging.** The bar is kept whole (not narrowed) in the revised doc; if checkpoint burn-rate makes the full bar untenable, the fallback is a staged bar (e.g. single-class alpha across CRB first). Operator decision at a checkpoint, not a teammate improvisation.
4. **RESOLVED — "durability" definition (§1 item 4).** QA flagged that the alpha bar's calculation list ("... AC, durability, carry capacity ...") is ambiguous between character survivability and item hardness/breakage; the codebase has no item-hardness/breakage mechanic anywhere. Ruling (lead, 2026-07-23): **durability = the character's displayed survivability stat — max/current HP, temporary HP, nonlethal damage tracking, and unconscious/dying/death thresholds** — distinct from "level-up hit points" (§1 item 4's separate entry), which is specifically the hit-die + Con-mod increment calculated during the level-up flow. This keeps the bar scoped to character-sheet mechanics already in the codebase's model and introduces no new game system. QA may proceed writing red-green tests against this definition. Follow-up (QA, same day): durability has almost no production surface either — only an isolated level-1 fighter HP value, no aggregate max/current/temp HP or dying-death fields anywhere — so this is a real wave-2 build item, not just a naming clarification.
5. **OPEN — Pets/animal-companion gap vs. alpha bar item 2.** Frontend's stub-tab audit confirmed Pets (animal companions) is a genuine pre-existing non-goal — `pilot_compute.rs` marks it "named-but-unproven," no stat-block engine exists at all. This is not something the swarm broke; it predates the swarm. But bar item 2 requires creating "a character of any class or race from the four primary books," and Druid, Ranger (level 4+), Hunter (ACG), and Cavalier (mount) all have companion/mount mechanics as core class features. Reading: **not a literal blocker** — items 2-4 don't explicitly name companion management as a required affordance, so those classes remain creatable/advanceable/calculable per the bar's literal text, just without a working companion. Flagging for explicit operator sign-off before final attestation rather than letting it fall out of scope silently — if the operator considers a functioning companion part of "any class" in spirit, this becomes a real (and large — no stat-block engine exists) wave-3+ item. Owner: operator, at a go/no-go checkpoint or final attestation review.

10. **RESOLVED — Wizard's compute-gate fix needed two follow-on fixes; both landed.** Frontend live-tested backend's Wizard fix (3484b5d) and found two further, independent gaps underneath it:
    - **RESOLVED — level-up path gap.** `apply_level_up` seeded zero choices for any class — only `compose_character_input` (character creation) was touched by 3484b5d, so multiclassing Wizard onto an existing character still hit the OLD diagnostic. Fixed in `1aabdf8`: seeds the same canonical choices in the new-class-entry branch only, guaranteed to fire exactly once per character (verified with a dedicated test — `wizard_has_canonical_specialization_selections` requires exactly 2 opposed-school entries, so a re-seed on a later level-up would break it, and doesn't).
    - **RESOLVED — bootstrap deadlock (the real bottleneck).** `create_character` only ever persists a proven-`Computed` build, so a fresh Wizard (empty spellbook) could never be saved in the first place. The Add Spell picker couldn't bootstrap around this either: `unmet_wizard_spellbook_conditions` requires one spell recorded as **both** `AcquisitionMode::Known` and `AcquisitionMode::Prepared`, but `add_spell_selection` only sets one mode per call, and `mutate_saved_character_at_root` discards (never persists) any call that doesn't independently reach `Computed` — so a Known-only call was discarded, a Prepared-only call was discarded, neither built toward the other. Backend's own earlier passing test only reached `Computed` by constructing `CharacterInput` directly in Rust, bypassing the command layer — real proof the compute logic was correct, not proof the UI could produce this state.

      **Root cause confirmed + fix landed (backend, 2026-07-23).** Backend independently re-derived the same root cause before reading the framing above (verification, not agreement-seeking) and confirmed the scope precisely: purely a bootstrap/chicken-and-egg problem for the *first* spell — once a character has ≥1 Known and ≥1 Prepared entry, subsequent single-mode `add_spell_selection` calls already work fine, so `add_spell_selection` itself needed no redesign. Landed as `record_and_prepare_spell_selection` (`6e12437`) — a new Tauri command whose mutation closure pushes both a Known and a Prepared `SpellSelection` entry (same spell) in one `mutate_saved_character_at_root` call, atomically satisfying both conditions on the first call, same additive-command shape as every other `add_*_selection` command, no changes to `add_spell_selection` or the never-persist-unproven invariant. Scoped Wizard-only, shape generalizes without rework if another prepared caster gets a similar gate later. Frontend now testing the actual spell-picker flow for the first time — this is the first point in the swarm where a live Wizard character with real spell selections is reachable through the shipped UI, not just the compute layer.

Correctly not attempted speculatively. Owner: backend or a dedicated future cycle, given the `.pcg`-authoring expertise the Fighter history implies — not squeezed into this wave.

Not a bug — explicitly disclaimed as out-of-scope in `explain_wizard_level1_prepared_spell_baseline`'s original doc comment when that function was first written. Clean, bounded, well-specified: `10 + spell_level + intelligence_modifier`, mirroring the exact existing pattern for the other 4 classes. QA correctly filed rather than fixed (production code, not their lane). Backend picking this up now.

## Risks

1. **Alpha-bar distance — SHARPENED, then SCOPED.** Current state (`docs/architecture/status.md`, 2026-07-23): only single-class Fighter 1–3 reaches a `Computed` receipt; 7 of 10 CharacterSheet tabs stubbed; Feat picker and Money panel do not exist; level-up/skill/bio persistence are no-ops. The §1 bar (6-level multiclass, four books, PCGen parity, zero stubs) requires multiple task waves; the go/no-go checkpoints in §6 are the containment mechanism. **Update (backend, task 2 delivery):** the compute engine's `Computed` path is narrower than "Fighter 1–3" implied — it currently only computes for one exact hardcoded posture. Any other skill/equipment choice returns `Blocked` with diagnostics rather than a receipt — pre-existing engine narrowness, not something the swarm introduced, but it means most tester choices through the newly-wired UI will hit Blocked, not Computed, until this is widened.

   **Full scoping (backend proposal, 2026-07-23, greenlit in part):** the narrowness is actually 4 independent exactness gates in `pilot_compute.rs`, each class-agnostic except one sub-check, any deviation trips `Blocked` with no partial credit:
   1. `unmet_combat_posture_conditions` — exact Longsword+Chain Shirt, no shield, Power Attack selected-inactive, Dodge+Weapon Focus feats (one Fighter-only sub-check).
   2. `unmet_selected_skill_posture_conditions` — exactly Climb/Intimidate/Swim rank 1, chain shirt equipped, nothing else.
   3. A Human-Wizard-only spellbook posture gate (level ≤3, canonical Evocation specialization, exact prepared spellbook) — newly found, wasn't previously documented, fires independently.
   4. AC specifically: `baseline_armor_class` (the gate) never calls `equipment_effects.rs`'s `compute_equipment_effects`, which already computes *real, correct* per-item AC deltas for arbitrary gear and is already wired into the separate desktop-UI equipment tab. The correct math exists and is simply disconnected from the gate.

   **Sizing by pillar (backend's original proposal):** AC — small-medium, a real wiring job (initially greenlit, scoped to Fighter/Wizard/Rogue: splice the existing correct math into the gate). Attack bonus — large, needs genuinely new equipment-driven to-hit math that doesn't exist (feats/enhancement bonuses only today). Skills — medium-large: `allocate_skill_ranks` only maps 5 skills, class-skill recognition is Fighter-only, and has no armor-check-penalty term at all (explicitly deferred in its own doc comment) — not a drop-in fix even for the 5 skills it knows. Wizard spellbook gate — separate, untouched by the above.

   **AC SLICE DROPPED — the real finding is architectural, not per-pillar (backend, mid-implementation, 2026-07-23):** the original AC sizing assumed the correct per-item math could be spliced directly into the gate. It can't, cheaply. `compute_combat_baseline`/`baseline_armor_class` (the thing that gates `Computed`/`Blocked`) lives in the **headless** compute layer — `build_pilot_headless_receipt`/`compute_pilot_base_chassis` take a `CharacterInput` only, **no corpus parameter**, by design. Real per-item AC values only exist via `equipment_effects::arms_armor::compute_arms_armor_effect`, which needs a corpus-resolved `EquipmentRecord` — corpus access the headless layer structurally doesn't have. The static, corpus-free `equipment_tables()` carries no AC-bonus field at all. Bridging this means either (a) threading a corpus parameter through the entire headless chassis call chain — ~347 call-site grep hits, a blast radius comparable to or bigger than task 4's Rogue widening — or (b) moving the `Computed`/`Blocked` decision itself to the corpus-aware layer (`pilot_compute_corpus.rs`'s `compute_pilot_with_corpus`, which already has both), a real architecture decision about which layer owns claim-gating, not an implementation detail. Backend caught this *before* writing the change and stopped to ask rather than push forward on unscoped work or fabricate a corpus-free approximation — correct call, no code written.

   **Decision:** dropped for this swarm. Option 1 (leave the gate alone, since the corpus-aware desktop equipment tab already shows real AC for arbitrary gear today — that's existing behavior, not new work) is close to a no-op and not worth landing on its own. Option 2 (the corpus-threading/layer-ownership change) is a genuine future epic, not a wave-2 item — **flagging for the operator**: this likely isn't just an AC problem. If attack-bonus and general-skill widening (already sized large/medium-large above) hit the same headless/corpus-aware split, bridging that one architecture boundary might be the actual unlock for all three posture-narrowness pillars at once, rather than three independent slices. Worth a dedicated scoping pass before any future wave attempts AC, attack-bonus, or skill-posture widening again. Backend proceeding instead to items 2-4 (durability, money-conversion PCGen verification, comparator field-extraction), none of which share this problem.

   **Follow-up scoping pass, answered precisely, split by dimension (backend, 2026-07-24, read-only, no code).** Confirms the hypothesis for two of the three remaining pillars, refutes it for the third:
   - **Attack-bonus widening: YES, same wall, confirmed exactly.** Real to-hit for arbitrary weapons needs `equipment_effects/equipmods.rs`'s `compute_equipmods_effect`, which reads a weapon's magic enhancement bonus (`WeaponEnhancementBonus`, the corpus's `BONUS:WEAPON|TOHIT|...|TYPE=Enhancement` token) off a corpus-resolved `EquipmentRecord` — same structural requirement as AC's `compute_arms_armor_effect`. The static, corpus-free `equipment_tables()` table carries nothing enhancement-related.
   - **Skill-posture widening splits into two genuinely different sub-problems.** (1) Armor-check-penalty for arbitrary armor: **YES, same wall** — the real corpus record's `ACCHECK:` token exists (verified against `Leather Armor (Base)`, `ACCHECK:0`) but the static `equipment_tables()` doesn't carry it. (2) Class-skill-list recognition (which skills are class skills for Wizard/Rogue/Cleric/etc., beyond the already-fixed Fighter/Rogue case): **NO, this is NOT corpus-blocked** — it's a labor-volume problem, not an architecture wall. This data isn't in any static table today, but it doesn't need corpus access to get there: it can be hand-authored as literal per-class skill lists, exactly the existing `GROUNDED_FIGHTER_CLASS_SKILLS` precedent already used in `skill_allocation.rs`.
   - **Bottom line for the future-epic writeup:** bridging the headless/corpus-aware boundary would genuinely unlock both AC-shaped gaps (attack-bonus enhancement, skill ACP) at once — confirms the hypothesis for those two dimensions specifically. It would **not**, by itself, close the class-skill-list gap, which needs separate hand-authored per-class data regardless of which layer owns the gate. Both halves stated explicitly so a future scoping pass doesn't overstate what the architecture fix alone would buy.

4. **RESOLVED — "durability" definition (§1 item 4).** QA flagged that the alpha bar's calculation list ("... AC, durability, carry capacity ...") is ambiguous between character survivability and item hardness/breakage; the codebase has no item-hardness/breakage mechanic anywhere. Ruling (lead, 2026-07-23): **durability = the character's displayed survivability stat — max/current HP, temporary HP, nonlethal damage tracking, and unconscious/dying/death thresholds** — distinct from "level-up hit points" (§1 item 4's separate entry), which is specifically the hit-die + Con-mod increment calculated during the level-up flow. This keeps the bar scoped to character-sheet mechanics already in the codebase's model and introduces no new game system. QA may proceed writing red-green tests against this definition. Follow-up (QA, same day): durability has almost no production surface either — only an isolated level-1 fighter HP value, no aggregate max/current/temp HP or dying-death fields anywhere — so this is a real wave-2 build item, not just a naming clarification.

    **Backend build landed, frontend never followed (backend's DTO-consumption sweep, 2026-07-24): full command/DTO shapes for whoever wires the UI, so this can be picked up cold.**

    - **`load_character_durability`** — request `{ characterId: string }` → `Result<CharacterDurabilityDto, string>`. Errs (not a `Blocked`-style payload, a rejected IPC call) when the saved build isn't single-class Fighter/Wizard/Rogue at a level `durability::compute_max_hp` recognizes — same scoping restriction the compute layer already has elsewhere, not new. A Durability tab needs to handle this the same way other tabs handle an unsupported-class build (a "not available for this build" fallback), not treat it as an unexpected failure.
    - **`adjust_character_hp`** — request `{ characterId: string, deltaHp?: number, deltaNonlethal?: number }` (both default 0) → same `CharacterDurabilityDto`, recomputed. **This is already atomic and delta-based, not two calls needing client-side coordination** — unlike the money/equipment-purchase coupling this doc flagged earlier, there's no read-then-compute-then-write race to design around: send `deltaHp: -8` to deal 8 lethal damage, `deltaNonlethal: +5` to add 5 nonlethal, and the server clamps (`current_hp` capped at `max_hp` on healing, `nonlethal_damage` floored at 0 on recovery) and reclassifies `status` in the same call. A "type an absolute new HP value" input just needs `deltaHp = newValue - currentHp` computed client-side before the one call — still one round trip, not two.
    - **`CharacterDurabilityDto`'s 4 fields, in PF1 terms**: `maxHp` — the character's ceiling, computed fresh from class hit die + Con modifier each load, never stored. `currentHp` — the live tracked value, persisted in a `hp.json` sidecar, defaults to `maxHp` the first time a character is loaded (no special "initialize" call needed). `nonlethalDamage` — PF1's separate nonlethal pool, persisted alongside `currentHp`; `currentHp` itself is never reduced by nonlethal damage. `status` — a pre-computed label, one of `Normal` / `Staggered` (`nonlethalDamage == currentHp`) / `Disabled` (`currentHp == 0`) / `Unconscious` (`nonlethalDamage > currentHp`) / `Dying` (`currentHp < 0`) / `Dead` (`currentHp <= -constitutionScore`) — a minimal UI can render this string directly (e.g. as a badge/color) rather than re-deriving thresholds client-side.
    - **What doesn't exist yet, flagged so it isn't assumed**: no temporary HP field (already noted above as explicitly out of scope for this wave); no dedicated "heal to full"/"stabilize" convenience call (achievable client-side as `deltaHp: maxHp - currentHp`, just not a named single-purpose command); no death-save/stabilization mechanic beyond the `Dying`/`Dead` labels themselves (labels only, no dice-roll flow) — consistent with the alpha bar not naming that affordance.
    - **Net for whoever builds this**: the backend side is a clean, already-atomic read/write pair with no coupling hazard to design around — the missing piece is purely a new HP display + a damage/heal input calling `adjust_character_hp`, no new backend work anticipated for a minimal version.

    **Status thresholds verified against real PF1 rules, not just internal consistency (backend, 2026-07-24).** `classify_durability`'s exact formula (`durability.rs:99-113`) checked against the real d20/PF1 "Injury and Death" and "Nonlethal Damage" rules: Dead (`current_hp <= -constitution_score`, correctly the Constitution *score* not modifier), Dying (`current_hp < 0`), Disabled (`current_hp == 0`), Unconscious (`nonlethal_damage > current_hp`), Staggered (`nonlethal_damage == current_hp`), Normal (fallthrough) — all 6 match. One precedence question confirmed deliberate: at `current_hp == 0` with `nonlethal_damage == 0`, Disabled and Staggered are both literally true, but the `if/else if` order checks Disabled first — correct, matches the real ruling that 0-hp-Disabled is the more specific controlling rule. **Sourcing caveat stated plainly**: no local PCGen corpus source contains this rule text (checked; PCGen's data only references these conditions as effects *caused by* specific abilities, not the core rules defining the thresholds) — verified against the well-established, unchanged-since-3.5e d20 SRD Open Game Content text instead, same sourcing category as `money.rs`'s already-flagged pp/gp/sp/cp ratio. Clean result, no mismatch — safe for frontend to render these labels as ground truth.

    **Backend half landed, frontend half never started (backend, 2026-07-24, DTO-consumption sweep).** `CharacterDurabilityDto` (`maxHp`/`currentHp`/`nonlethalDamage`/`status`) and its two Tauri commands (`load_character_durability`, `adjust_character_hp`) are real, registered, computed, and fully tested backend-side — but frontend has zero `invoke()` calls for either command and zero components/tabs mentioning "durability" anywhere (case-insensitive grep, zero hits). `CreateCharacterForm.tsx`'s own `maxHp` is a separately-computed client-side local value, not a read of the backend DTO. Matches the untracked/unattributed `SWARM_TASKS.md`'s durability row still showing "queued" (that file's overall claims are not trusted, per the earlier flag, but this one line happens to be independently confirmed true).

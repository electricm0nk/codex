  ## Three real, non-fabricated sources that raised the ceiling (1821 → 2021 / 2977, 61.2% → 67.9%)

  **1. Ingestion bug fix (no web source; 67 `arms_armor.rs` records).** `cr_equip_arms_armor.lst` has 67 rows using the corpus's `DESC:.CLEAR`-then-`DESC:<real text>` convention (a `.COPY=` variant explicitly clearing an inherited description and replacing it with its own — e.g. `Bolt (Screaming)`, `Arrow (Slaying)`, `Padded Barding (Base)`). Direct inspection of `parse_equipment_file`'s output confirmed the tokenizer already preserves *both* `DESC:` tokens per row in source order; the bug was in the original SD-24 ad-hoc codegen script, which only captured the first `DESC:` token and stored the literal string `.CLEAR` in 67 shipped `EquipmentTableEntry` records. Verified against the raw LST directly (`grep -oP 'DESC:\.CLEAR\tDESC:[^\t]*'` → 67/67 have a real follow-up `DESC:`, 0 truly-cleared-with-nothing-after cases). Fixed by re-deriving the effective description (last `DESC:` token, decoded) directly from the corpus for all 147 arms_armor records that carry any `DESC:` token at all (80 were already correct — cross-checked byte-for-byte, 0 mismatches — confirming the fix touches only the 67 broken ones).

  **2. `.COPY=`-inheritance (register A11; no web source; 117 records — 98 in `arms_armor.rs`, 19 in `general.rs`).** A `.COPY=`-derived record (e.g. `Arrow`, a purchase-quantity SKU of `Arrow (Base)`; `Padded`, a material variant of `Padded Armor (Base)`; `Barding (Padded)`, a barding variant of `Padded Barding (Base)`) carries no `DESC:` token of its own in the corpus, but the existing codegen already stores its copy-source's key in the `name` field (verified against `extract_record_name`'s real behavior and the raw LST's `<SourceKey>.COPY=<NewName>` convention). Inheriting the source record's already-corpus-sourced description is applying the LST's own declared data-inheritance convention, not fabrication — resolved transitively (2 iterations needed for barding chains, since a barding record's own base is itself one of the 67 `.CLEAR`-bug records from source #1, fixed first so the inheritance picks up the *correct*, barding-specific text rather than the wrong armor-type text a naive single-pass propagation would have produced). A record whose own base *also* has no description (e.g. `Dart (Blowgun)` ← `Blowgun Dart (Base)`, which genuinely carries no `DESC:` token in the corpus either) correctly stays `None` — no fabrication when there is nothing to inherit.

  **3. Bounded d20pfsrd.com web-second-source pass (83 `cr_equipmods.lst` records; 50 distinct identity-matched names).** Fetched 2026-07-22, reasonable pacing (one fetch per distinct real named concept, no bulk scraping):

  - Weapon special abilities (`https://www.d20pfsrd.com/magic-items/magic-weapons/magic-weapon-special-abilities/<slug>/`): Flaming, Frost, Shock, Ghost Touch, Keen, Vorpal, Holy, Unholy, Bane, Speed, Wounding, Anarchic, Axiomatic, Brilliant Energy, Defending, Disruption, Flaming Burst, Icy Burst, Shocking Burst, Thundering, Vicious, Merciful, Mighty Cleaving, Spell Storing, Dancing, Distance, Returning, Seeking, Throwing.

  ## New `## DISCOVERED` finding: duplicate-KEY shell records in `equipmods.rs` (out of this cycle's scope)

  While building the web-sourced patch, found that **314 of `equipmods.rs`'s 658 entries share an identical `key` string with another entry in the same table** (344 unique keys, not 658) — e.g. `Material ~ Adamantine ~ Ammunition` appears twice: once as the real, populated record (`name: "Adamantine"`, `cost_gp: Some(60.0)`) and once as a near-empty self-referential shell (`name: "Material ~ Adamantine ~ Ammunition"` — identical to its own `key`, `cost_gp: None`). This contradicts the module's own doc comment ("658 records, one per distinct item after the SD-17 KEY:-based merge fix") and means `records_expected: 658` for CRB equipmods likely overcounts real distinct content by ~314. Confirmed isolated to `equipmods.rs` only (`general.rs`/`arms_armor.rs`/`magic_items.rs` all have unique keys matching their totals). **Not fixed in this cycle** — deduping would change the hard-coded `658`/`2977` totals several existing SD-24 tests assert exactly, is a larger and separate correctness fix from "populate the description field," and risks unintended interaction with the 3 concurrent sibling worktree cycles also touching adjacent corpus-intake files this same phase. My own web-sourced patch is unaffected in correctness (the `KEY_OVERRIDES`/name-based lookup applied the same, correct text to both the real Ghost Touch armor record and its duplicate shell — harmless redundancy, not a wrong value), but a future cycle should investigate and, if confirmed, correct `records_expected`/re-derive the true CRB equipmods record count from the corpus directly.

## The real fix: two dedicated, verified probes

Read `explain_ranger_level1_chassis_and_class_feature_separation` (`src/rules_core/pilot_compute/mod.rs`)
directly before building anything, confirming two facts, never assumed:

1. **Every one of the 31 `"Favored Enemy Bonus ~ <type>"` corpus records
   (`data/corpus/core_rulebook/class_feature/favored_enemy_bonus/*.json`) carries the identical
   shape**: `description: null`, `PREABILITY:1,CATEGORY=Special Ability,Favored Enemy ~ <type>`,
   and a flat, literal `BONUS:VAR|Favored<Type>|2` token — never a per-level or ability-derived
   formula. The 11 `"Favored Terrain Bonus ~ <type>"` records are the identical shape one level
   later (`BONUS:VAR|FavoredTerrain<Type>|2`, `PREABILITY` on `Favored Terrain ~ <type>`).
2. **The engine's own real computation of the flat `+2` skill/attack-damage magnitude is generic**:
   `choice_selection(input, "choice:ranger_favored_enemy")` is echoed into a `+0`
   `"class_chassis.ranger.favored_enemy_choice"` recognition record with NO restricted-list
   validation (any string round-trips), and the separate flat `favored_enemy_bonus: i16 = 2 + ...`
   computation (`"class_chassis.ranger.favored_enemy_skill_bonus"` /
   `"...attack_damage_bonus"`) is identical regardless of which type was chosen — because
   `FavoredBaseBonus`, the corpus's own shared per-type variable, IS the same class-wide bonus the
   engine computes independently. So a real, live `compute_pilot_base_chassis` run genuinely
   reproduces each record's own literal `2` for ANY of the 31/11 canonical type strings — unlike
   Weapon Training's hardcoded 4-of-52 subset, this is not narrowing to a special case; it is
   confirming, per canonical name, that the exact string each record's own `PREABILITY` names
   round-trips end-to-end and that the OBSERVED magnitude equals that record's own literal token,
   never assumed without observing it. `canonical_seeds_for("ranger")` never seeds either choice
   at all (confirmed by grep), so the standard sweep never observes any of these on its own.

Built `probe_ranger_favored_enemy_bonus_wiring` and `probe_ranger_favored_terrain_bonus_wiring`
(`src/bin/v06_work_inventory.rs`), the same shape as `probe_domain_power_effect_wiring` /
`probe_fighter_weapon_training_wiring`: for each of the 31 / 11 canonical type strings
(transcribed verbatim from the corpus's own `PREABILITY` token, never derived by string
transformation — two entries, `Humanoid (...)` and `Outsider (...)`, would not round-trip through
a naive strip/replace), select the real choice, sweep `SWEEP_LEVELS` through the real
`compute_pilot_base_chassis` pipeline, and keep only the type names whose choice-recognition AND
`value == 2` magnitude explanations were BOTH genuinely observed. `classify()`'s `Kind::ClassFeature`
arm gained two new early checks (mirroring the Domain Power / Weapon Training checks exactly):
grounds `"Favored Enemy Bonus ~ <type>"` / `"Favored Terrain Bonus ~ <type>"` only when the probe's
own observed set contains that exact type.

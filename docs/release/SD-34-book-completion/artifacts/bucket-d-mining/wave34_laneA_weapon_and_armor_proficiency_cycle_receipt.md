## Notes

- **The wave-33 receipt's own next-cycle plan assumed "all five of these classes have real
  archetypes doing exactly that."** That assumption held for Bard, Fighter, and Paladin, but not
  for Ranger or Rogue — every registered archetype for both classes was read individually and
  none supersedes their weapon/armor proficiency slot in this engine's catalog. Logged as a
  correction (`scripts/retro.py correction`, subject `wave33-lane-a-receipt`).
- **The Divine Hunter fabrication hazard the dispatch named directly was real, not
  hypothetical.** Divine Hunter's own `replaces` list carries `PaladinArmorProficiencyHeavy`
  alone; had that slot id been included in Paladin's `proficiency_slot_ids` list (a plausible
  mistake — the slot id contains "Paladin" and "Proficiency", it would grep-match a naive
  pattern), a Divine Hunter selection would wrongly claim the base progression "does not apply,"
  fabricating a loss of light/medium armor and weapon proficiency the archetype never actually
  takes away. `paladin_weapon_and_armor_proficiency_divine_hunter_does_not_supersede_the_base_
  grant` pins the correct behavior directly.
- **`v06_work_inventory.rs`'s classify() branch needed a second fix beyond `pilot_compute`
  wiring**, which the wave-33 receipt's own comment did not anticipate: this record shape's
  reversed corpus key (`"Weapon and Armor Proficiency ~ <Class>"`) means `class_feature_owner`'s
  `group == class name` guard can never resolve an owner for it, so the file's generic
  `class_feature_exact_suffix_grounded` promotion path — the one that promotes Cleric/Sorcerer/
  Wizard once `pilot_compute` grounds them — structurally cannot reach these five units, ever
  (`class_feature_owner_via_type_facet`'s own doc comment proves this is by design). The named-
  list branch this shape already had (`weapon_and_armor_proficiency_grant_class_id`) needed its
  own direct `facts.explanation_ids` check added.

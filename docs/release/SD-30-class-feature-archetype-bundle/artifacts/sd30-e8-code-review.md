## SD30-E8-F3 — Findings triage

### Finding 1 — dangling grant reference on a future PI-dropped class feature

| | |
|---|---|
| **File** | `src/bin/ingest_pu_classes.rs` |
| **Severity** | medium |
| **Disposition** | **fixed-in-bundle** |
| **Reviewer's proposed disposition** | deferred |

**Verified true by content.** `variant_grants` was captured and written into the class-variant
record (`ClassVariantCacheData.feature_grants`, persisted via `write_record`) *before* the
per-feature-row loop's own `NAMEISPI:YES` drop check ran. A future PI-dropped feature row would
ship a dangling grant reference in the class-variant JSON with no corresponding `class_feature`
record on disk — a shipped record promising a feature the corpus does not provide. Currently latent
(0 live `NAMEISPI:YES` rows in the only ingested source, re-confirmed this cycle:
`grep -oE 'NAMEISPI:[A-Za-z]*|DESCISPI:[A-Za-z]*' ~/workspace/repos/pcgen/data/pathfinder/paizo/roleplaying_game/pathfinder_unchained/pu_abilities_class.lst`
→ no output).

**Fix.** Extracted a new `drop_pi_named_grants(variant_grants, feature_rows) -> Vec<ClassFeatureGrant>`
pure function, called *before* `feature_grants` is captured into the record, filtering out any
grant whose `feature_key` names a feature row `declared_product_identity_of` reports
`NAMEISPI:YES` on — mirrors `ingest_race_traits.rs`'s own drop-before-chassis-derivation ordering,
the precedent this code already said it followed but did not reproduce.

**Test.** `drop_pi_named_grants_removes_only_the_grant_naming_a_nameispi_row` — plants a clean
feature row, a `NAMEISPI:YES` row, and a grant naming neither (an orphan, a *different*,
pre-existing check's own concern) and proves the function drops only the PI-named grant, keeps the
clean one, and does not over-drop the orphan. `cargo test --locked --bin ingest_pu_classes`: 24/24
pass (was 23; +1 new).

**Re-derivation confirming no regression.** `cargo run --locked --bin ingest_pu_classes` regenerated
against the live corpus; `git diff -- data/corpus/pathfinder_unchained/` showed **only**
`ingested_at` timestamp changes across all 68 touched files (confirmed via
`git diff -- data/corpus/pathfinder_unchained/ | grep -v '^ ' | grep -E '^[+-]' | grep -v '^+++\|^---' | grep -v ingested_at`
→ no output) — the fix is a no-op on today's shipped data, exactly as expected with 0 live
`NAMEISPI:YES` rows. The timestamp-only regen was reverted (`git checkout -- data/corpus/pathfinder_unchained/`)
since it carried no substantive change.

Retro: `correction` `1786761343834-sd30-e8-triage-18a374`.

### Finding 2 — DoD item 3's gate not wired into `verify.sh`, zero test coverage for the citation-drift fix

| | |
|---|---|
| **File** | `src/pcgen_import/corpus_traps.rs` |
| **Severity** | medium |
| **Disposition** | **fixed-in-bundle** (test-coverage gap AND a real residual correctness bug the coverage gap was hiding); **deferred** (wiring into `scripts/verify.sh`) |
| **Reviewer's proposed disposition** | deferred |

**Verified true by content**, then investigated further than the finding itself asked. The
reviewer's ask was narrow: add a scratch fixture for a citation nested under a book subdirectory
(none of the three pre-existing `ScratchAudit` fixtures exercise that shape) and confirm
`audit_ingested_cache`'s `SD30-CARRY-001` `book_dir` fix handles it.

Building that fixture naively (nesting the file directly under `test_book/…` with no directory
prefix in `source.path`) passed — but for the wrong reason: `ScratchAudit`'s own citations carry no
directory segment before the book name, so the `/{book}/` marker branch the fix actually added
never engaged; the fixture silently exercised the pre-fix `.parent()` fallback instead. Rebuilding
the fixture with a directory-prefixed path (`roleplaying_game/test_book/support/…`, matching every
real corpus path's shape) went **RED**: the self-check computed `display` (blank-content default)
instead of `derived`, because the fix's `file_basename` was still a bare
`Path::new(rel).file_name()` — dropping the `support/` segment `book_dir` itself had just been
widened to require. `CorpusLines::line`'s single-level `dir.join(file)` join then silently resolved
to a nonexistent path and `unwrap_or_default()` swallowed the failure.

**This is a real, currently-live defect**, not just a coverage gap: re-running
`cargo run --locked --bin v06_corpus_trap_report -- --audit` against the real corpus with the
`book_dir` half of the fix corrected (but `file_basename` still bare) surfaced **3 real production
defects** — `monster/psychopomp_ahmuuth.json`, `monster/steward_of_the_skein.json`,
`monster/the_first_blade.json` in `data/corpus/inner_sea_gods/`, all citing
`pathfinder/paizo/campaign_setting/inner_sea_gods/support/isg_races_b4.lst`, all shipped with
`wiring_class: "ambiguous"` (`no_corpus_line`) where their real `BONUS`/`DR` tokens call for
`derived`. (First observed as exit 0 with 3 printed defects — an authoring mistake in this cycle's
own first check, piping the exit code through `tail` and reading `tail`'s exit code instead of
`cargo run`'s; corrected immediately by re-running with the exit code captured directly in the same
shell statement, per this package's own doctrine. `TRAP_AUDIT_EXIT=2`, a real defect, confirmed.)

**Fix, part A (the audit self-check).** `file_basename` now preserves the citation's path tail past
the `/{book}/` marker (mirroring the same marker `book_dir` already uses) instead of a bare
basename, falling back to the bare basename only when the marker is absent (the `.parent()`
fallback shape, where `book_dir` already equals the file's own containing directory).

**Fix, part B (the generator itself — the deeper finding).** Investigating *why* the audit and the
shipped stamp disagreed (rather than just accepting the audit as newly-authoritative) traced the
disagreement to `src/bin/gen_book_cache.rs`'s `wiring_class_for_source`, the function that
originally computed and stamped these 3 records: it has the **identical** bare-basename bug
(`path.rsplit('/').next()`), confirmed by `gen_book_cache.rs`'s own `load_corpus_file_rel` doc
comment, which *already* names this exact hazard for a sibling code path ("`inner_sea_gods` keeps 3
monster rows and 16 ability rows under `support/`... joining onto the root there fails outright")
but the fix that comment describes (`resolve_book_file`'s recursive walk) only covers
citation/sha256 resolution, not the separate `wiring_class_for_source` call. Added
`wiring_class_file_arg(book_id, path)`, the same marker-based derivation, and a `book_id()` accessor
on `WiringClassIndex` (previously private) so `wiring_class_for_source` can compute it without a
signature change at every one of its 9 call sites.

**Regeneration.** `cargo run --locked --bin gen_book_cache -- inner_sea_gods` (the book's own
already-wired generator — a mechanical regen of already-shipped content, not new ingest or PI
screening, using the same generator `SD30-CARRY-001`'s own 10-book re-ingest already used for this
class of DoD-3 fix). `git diff -- data/corpus/inner_sea_gods/` shows exactly 116 files touched:
`ingested_at`/`LICENSE.json`'s `classified_at` timestamp bumps (regen noise, matching precedent)
across all of them, and **exactly the 3 expected `wiring_class`/`wiring_class_signals` field
changes** — confirmed via
`git diff -- data/corpus/inner_sea_gods/ | grep -v '^ ' | grep -E '^[+-]' | grep -v '^+++\|^---' | grep -v ingested_at`.
No other field, on any of the 116 records, changed.

**Tests.**
- `wiring_class_mismatch_reads_a_citation_nested_one_level_under_a_book_subdirectory`
  (`corpus_traps.rs`) — proven RED against the pre-`file_basename`-fix code (own construction, not
  narrated), GREEN after.
- `wiring_class_file_arg_keeps_the_subdirectory_a_bare_basename_would_drop`,
  `..._is_the_bare_basename_when_the_citation_sits_at_the_book_top_level`,
  `..._falls_back_to_the_bare_basename_when_the_book_marker_is_absent` (`gen_book_cache.rs`, new
  `#[cfg(test)] mod tests`, this file had none before) — 3/3 pass.
- `cargo test --locked --lib -j 2`: 1777/1777 pass (unchanged count from the pre-cycle baseline —
  no regression).

**Re-derived, final state.**
`cargo run --locked --bin v06_corpus_trap_report -- --audit` — exit code captured directly:
`TRAP_AUDIT_EXIT=0`, `259 0 mod-record`, **no other defects**. Genuinely GREEN, not a fabricated
pass: this is the same command that reported the 3 real defects two runs earlier, over corpus data
this cycle's own regen changed.

**Deferred (not fixed): wiring `v06_corpus_trap_report -- --audit` into `scripts/verify.sh`.** The
audit is now a real, non-vacuous gate (this cycle proved it can both fail and pass), which was the
previously-blocking objection to wiring it in — but *which* books/kinds it should cover
corpus-wide, and how a future legitimate `no_corpus_line` record is told apart from a future real
regression, is a repo-wide gate-shape decision beyond `epic-8-code-review`'s own remit, and SD-30's
scope note bars extending into moved-epic (ingest-lane) territory. Entered in
`forward-scope-register.md` Class 1, **C1.8**, owner `SD-31-corpus-closure-grind`.

- **Acceptance criterion (verbatim from epic-breakdown.md):** **A `+N` keeps the copy's facts** *(discovered by E4.9)*. A copy's key is `(item_id, bonus, ordinal)` (`selection_copy_keys` → `equipment_sets::copy_keys`, the bonus read by `engine_copy_bonus` from `applied_modifiers`), and `equipment_sets.json` keys every fact (`CopyFacts.name`, `size`, `properties`, the three overrides, `quantity`) and every set entry by it. `attach_equipment_modifier_priced_at_root` (`desktop/character_hub.rs`) pushes a `+N` onto the selection and saves, and nothing re-keys the sets file: the copy moves to `(item, N, k')`, and the later plain copies of its item number down without their facts following. **Verified (E4.9, a throwaway probe test on its tree):** two `Dagger (Base)`, copy 0 renamed "Grandpa", `+1` attached to copy 0 through the new `copy` field → held rows `[("+1 Dagger", bonus 1), ("Grandpa", bonus 0, copy (Dagger,0,0))]` — the name stayed on the key and landed on the **other** dagger. The same holds for a container copy's contents' `Inside` entries and a worn copy's slot entry. E4.9's Customize dialog makes this reachable in two clicks (rename, then Attach modifier on the same copy). **The card:** when an attach changes a copy's bonus, the sets file follows it — the facts and every set entry naming the old key (as copy or as container) move to the new key, and the old key is forgotten the way `forget_copy_in_sets` renumbers after a removal (one helper for both, no second renumbering). Tests: `rekey_on_bonus_` — the rename probe above (name stays on the +1 copy, the plain one reads "Dagger"); a +1 on a Sack-held dagger stays inside the sack; a +1 on copy 0 of three leaves copies 1 and 2's names on them; the Market's buy-a-`+N` path (new copies) unchanged.
- **What changed:** the attach records every saved line's `CopyKey` before the save (`selection_copy_keys`) and reads them again after it; when they differ (a `+N` changed a bonus), it maps old → new by saved line (an attach reorders no line) and moves the sets file through that map with `rekey_copies_in_sets`: every set entry's copy and `Inside` container, and the `copies` facts map, all at once. `forget_copy_in_sets` is the same helper with a removal's map (`removed` → forgotten, later ordinals of its item and bonus down by one), so there is one renumbering, not two. A modifier that leaves every key the same writes nothing.

## Result: 185 of 185 rows reach Computed. The histogram is empty.

`mix_panel_computed=185 mix_panel_blocked=0` — every mix in the panel
reaches `HeadlessReceiptStatus::Computed` under the census's own shared
canonical fixture (`codex::rules_core::class_seeds`), with zero
claim-blocking diagnostics. There is no "top blockers" table to report
this batch: the blocking-diagnostic-id histogram
(`mix_panel_blocking_histogram` in `census-f0d.json`) is `{}`.

**Why, read from the code (not guessed):** each panel row's own
originating test asserts Blocked against **that test's own,
individually-tuned fixture file** — which usually carries some deliberate
incompleteness elsewhere (an unset skill-point allocation, an unresolved
choice, etc.) that keeps the WHOLE receipt Blocked for a reason unrelated
to the multiclass mix itself. The census instead builds every mix from
ONE shared, already-complete canonical fixture plus
`class_seeds::canonical_seeds_for` (the exact machinery F0c's prestige-mix
sweep already uses, `input_for_mix` in
`src/rules_core/class_census.rs`), and every one of the 11 classes this
panel exercises (barbarian, bard, cleric, druid, fighter, monk, paladin,
ranger, rogue, sorcerer, wizard) is already in F0b's own measured
42-of-61 Computed-alone set
(`docs/release/SD-36-consolidation/artifacts/epic-f/census-f0b.json`).
Pairing any two already-Computed-alone classes under a build that is
otherwise complete introduces no NEW claim-blocking diagnostic — the
multiclass gate (`multiclass_class_level_supported`,
`class_occult_and_psionic.rs:748-755`) correctly withholds each class's
own bounded, level-gated chassis explanations (verified directly: the
`barbarian`/`fighter` level-10 mix's receipt carries exactly
`class_feature.barbarian.rage_execution.not_raging` and
`class_feature.fighter.weapon_and_armor_proficiency` — the un-bounded
recognition records every negative control's own prefix/exclude rule
already expects — and nothing else from either namespace), but withholding
those explanations does not, by itself, block the receipt.

This is a real, engine-derived measurement, not a fabricated one — every
row's `blocking_diagnostic_ids` is read straight off
`ComputationResult::diagnostics` (`d.claim_blocking`), the same field
every other census sweep in this file reads. See
`src/rules_core/class_census.rs`'s
`sweep_mix_panel_row_reports_a_real_status_and_dedupes_blocking_ids` test
for the specific barbarian/fighter trace this finding is built on.

## What this answers, and what it does not

§5's own words: *"What claim-blocks `[barbarian 12, fighter 1]` is not
measured yet — F3 code does not start before that histogram exists."*
This batch's measurement answers it precisely: **under the census's own
canonical fixture, nothing does.** F3 (multiclass BAB/save/HP/skill-point
computation) is not blocked by this panel's own inputs the way the
original review finding anticipated — every class this panel covers
already reaches Computed in a mix. F3's own work list therefore needs a
DIFFERENT measurement to find real claim-blocking shapes: either a
deliberately incomplete mix fixture (mirroring what each negative
control's own bespoke fixture withholds), or classes outside this panel's
11 (the other 50 non-prestige ids, 19 of which are Blocked even alone per
`census-f0b.json`) paired into a mix. This panel does not claim to have
swept those; it reports honestly what it did sweep, and that the result
was uniformly Computed.

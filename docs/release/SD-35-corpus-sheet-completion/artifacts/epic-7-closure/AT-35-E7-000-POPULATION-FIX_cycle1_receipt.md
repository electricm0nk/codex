## The fix: why this predicate, and why not the ten rows

`has_classifying_token` tested one token per kind — `TYPE:` for a feat, `SCHOOL:`/`CLASSES:` for a
spell — as a **proxy** for "this row declares a record of its own rather than pointing at one". The
proxy is sound in one direction only: a row carrying the token **is** a record; a row missing it is
**not thereby** a non-record. That is `AGENTS.md` rule 7 exactly — a filter that passed every case
anyone tested and was silently wrong on the shapes nobody did.

An id allow-list, a `pathfinder_unchained` exemption or a `pu_feats.lst` special case would each
have made the ten pass **and left the next such row silently dropped**, which is the defect itself.
So the predicate moved. Under the sheet rule (`decisions.md §1`) DONE is the rule's words on the
page, so the honest test for "this row is a record" is **does the row carry the rule's words**:

```rust
Kind::Feat  => has_token(fields, "TYPE:") || row_carries_rule_prose(fields),
Kind::Spell => has_token(fields, "SCHOOL:") || has_token(fields, "CLASSES:")
                                            || row_carries_rule_prose(fields),
```

`row_carries_rule_prose` is a non-empty, non-`.CLEAR` `DESC:` or `BENEFIT:`. A sub-choice helper —
the shape the trap exists to exclude — carries none of that: it is a gateway (`ABILITY:…|%LIST`), a
pick-list entry, or a bare header field, all pointer and no prose. This **generalises** the
reasoning `ability_row_has_content` already applies to `Kind::Ability`, rather than inventing one.
It is deliberately **narrower** than `ABILITY_CONTENT_PREFIXES` — prose only, no
`BONUS`/`DEFINE:`/`AUTO:` — so a pick-list row that restates a record declared elsewhere while
carrying a `BONUS:` is still refused.

## The stamp-loss condition, and why a new flag rather than `--allow-stamp-loss`

The guarded regen was **refused**, for a reason that is **not this cycle's**:

```
refusing to write docs/work-inventory.json: this run would drop 230 of the 32617 verification
stamp(s) … First offenders: advanced_class_guide:class_feature:admixture_savant_… (+9 more)
```

All 230 are `class_feature` units moving `sheet-complete` → `text-complete`, because
`class_feature_pool_catalog_holds` now returns true for them (evidence
`class_feature_pool_catalog_serves_a_rendered_description`) and `text-complete` is **not** in
`SHEET_COMPLETE_PROMOTABLE_STATUSES`. Both statuses are DONE, and that constant's own doc comment
says `text-complete` "sits ABOVE it and keeps its own word — already terminal", so this is a relabel
**upward** and costs zero completion. It is **pre-existing**: `AT-35-E6-003-RULED_cycle15_receipt.md`
records the identical 230, the identical first offenders and the identical rung line at cycle 14's
HEAD. **No cycle since has been able to regenerate `docs/work-inventory.json` at all.**

The dispatch forbids `--allow-stamp-loss`, and it is right to: that flag waves through **any** loss
of any size, including the one the guard exists to stop. Nor can the guard simply be taught to
ignore `grounded`/`text-complete`, because — measured, not assumed — the hazard lands on exactly
those statuses:

```
# the binary run WITHOUT CORPUS_LITERAL_SWEEP_REPORT / DERIVED_FIXTURE_CHECK_REPORT
UNGUARDED lost: 7615
  oracle-unverifiable -> grounded        6304
  oracle-agree        -> grounded         808
  sheet-complete      -> text-complete    230
  sheet-complete      -> grounded         217
  oracle-unverifiable -> text-complete     55
  oracle-agree        -> text-complete      1
```

`grounded` 7,329 + `text-complete` 286 = 7,615. **No status-set widening separates the hazard from
a legitimate supersession** — the separation has to be by **identity**. So the binary gained
`--expect-stamp-loss <declaration.json>`: the write proceeds only when the run's loss set is
**equal** to the declared id set; one undeclared loss, or one declared loss that did not happen, and
the write is refused and names the difference. The declaration is a committed file
(`b18-expected-stamp-loss.json`, 230 ids with their cause and their re-derive command), so the
losses a regen takes are in the diff and in review one id at a time, instead of being a number in a
receipt. This is `AGENTS.md` rule 8: the blanket flag was a warning, the equality is a control. It
is pinned by `declaration_parses_to_its_id_set`, `a_declaration_that_names_nothing_is_an_error` and
`only_an_exact_match_between_declared_and_lost_may_write`.

```
stamp-loss guard: 230 declared stamp loss(es) matched exactly; writing …/docs/work-inventory.json
```

**`--allow-stamp-loss` was not used, at any point in this cycle.**

## What this cycle does **not** cover

`AGENTS.md §7` makes the omission the load-bearing part.

1. **It does not re-derive the corpus denominator 48,864.** That is the census's figure, carried
   forward with its citation. This cycle moves the **numerator** from 48,854 to 48,864 and proves
   the ten render; it does not re-enumerate `data/corpus`.
2. **It does not fix the 230.** Their cause is named (`class_feature_pool_catalog_holds` widened,
   `text-complete` not promotable) and they are declared id by id, but whether a pool-catalog
   `text-complete` unit *ought* to promote to `sheet-complete` is a ladder question for
   `SHEET_COMPLETE_PROMOTABLE_STATUSES`, not for a predicate-widening cycle, and moving it would
   move thousands of units. Both statuses are DONE, so no figure in this bundle rests on the answer.
3. **It does not establish that every prose variant of a multi-variant `.lst` row prints** — the
   census's own open item 4, unchanged. The five admitted rows that resolved onto existing units are
   that shape.
4. **The widened predicate is proven against the pinned oracle SHA only.** A future corpus could
   carry a prose-bearing row of a shape neither predicate anticipated;
   `widened_predicate_census.py` is committed so the same measurement re-runs in one command.

   at cycle start** — `box_ledger.py --check` exits 1 because `THE-BOX.md` pins SD-33's status

   population string 49,438 → 49,450 because its own change moved the figure; it did not adopt the
   pre-existing red.

  ## Generation method (per `decisions.md §11.3`)

  `src/bin/sd26_gen_core_rulebook_cache.rs` is a one-off codegen tool (run once via `cargo run --bin sd26_gen_core_rulebook_cache`, not part of the shipped library or the test suite's runtime path) that iterates `rules_tables::crb`'s own public accessors — `ClassId::ALL` + `class_tables()` + `good_saves_for()`, `spell_list::SPELL_LIST`, `equipment_tables::equipment_tables()` — exactly the same accessor surface `corpus_ingest_diagnostic.rs` (SD-25 Epic 5) already calls. Every `data` field in the generated JSON comes directly from these compiled Rust values; the raw local PCGen corpus checkout (`~/workspace/repos/pcgen/data/pathfinder/paizo/roleplaying_game/core_rulebook/`, `PCGEN_CORPUS_ROOT` overridable) is read *only* to locate a real, checkable citation (file path relative to the corpus root, a real SHA-256 of the corpus file's bytes, and a real 1-indexed line number) for the discriminated `source` union — never to re-derive any value. This satisfies `decisions.md §11.3`'s explicit instruction not to re-parse raw LST for values while still producing honest, checkable, non-fabricated citations (rather than the alternative of omitting citations entirely).

  ## `source` provenance-kind detection (real, not guessed)

  For each equipment record, the generator inspects the real corpus line matching that record's `KEY:` token (or name-fallback, matching `EquipmentTableEntry.key`'s own documented fallback rule) and classifies:
  - **`lst_corrected_ingest`** if the line has a `DESC:.CLEAR` sentinel followed by a real `DESC:` token on the same row (the SD-25-fixed ingestion bug).
  - **`lst_token`** if the line has a real `DESC:` token directly (or no `DESC:` token at all and the record's own `description` is honestly `None`).
  - **`lst_inherited_copy`** if the line has no `DESC:` token, the record's `description` *is* `Some(...)`, and the line's own identity is a `.COPY=`-derived row (`inherited_from_record_key` is the corpus's own pre-`.COPY=` source-record identity, real and checkable even where it does not byte-match this cache's own `key` naming for that base record).
  - **`web_second_source`** if none of the above apply and the record's `name` matches one of the ~50 named concepts SD-25's own d20pfsrd.com pass covered (carried forward verbatim from `../SD-25-ui-evaluation-defect-closure/artifacts/epic_7/corpus-intake-crb-description_cycle_receipt.md`'s own citation list — materials page, weapon-special-abilities pages, armor-special-abilities pages; `Ghost Touch` disambiguated weapon-vs-armor by checking whether the record's own `key` contains `"Armor"`), with `fetched_at: "2026-07-22"` per that receipt's own stated fetch date.

  Class records use `lst_token` (real `CLASS:<Name>` line + line number in `cr_classes.lst`, found by requiring both `HD:` and `MAXLEVEL:` on the matched line to skip the class's own secondary/skill-point continuation rows). Spell records use `lst_token`, preferring the `<Name>.MOD` record's own line when it carries a real `DESC:` token (623/652 per `spell_list.rs`'s own doc comment), else the base record's line (the remaining 29) — matching the module's already-documented method exactly.

  **Real result: every single one of the 3,326 records (11 classes + 652 spells + 2,663 deduplicated equipment) was successfully attributed — zero records were skipped as unattributable.** No record was written with a fabricated or guessed `source`.

  ## Directory layout — one judgment call vs. `technical-design.md §3.2`'s illustrative example

  `technical-design.md §3.2` illustrates equipment paths as `equipment/{weapon,armor,shield,wondrous,consumable}/*.json` — CRB's real Rust data has no such subtype breakdown (only `EquipmentCategory::{ArmsArmor,General,MagicItems,Equipmods}`, matching the 4 real corpus files). Forcing records into the illustrative 5-bucket scheme would require guessing a subtype the data doesn't carry (a fabrication risk). **Used the real category enum instead:** `data/corpus/core_rulebook/equipment/{arms_armor,general,magic_items,equipmods}/*.json`. Documented here as a judgment call per this bundle's own "flag judgment calls" instruction.

  `completeness` for equipment records (the schema's 3-tier enum doesn't map perfectly onto equipment's flatter field set) is derived as: `full` when `description.is_some()`, `chassis_plus_extract` when `cost_gp`/`weight_lbs` is present but `description` is `None`, `chassis_only` otherwise. Classes use `chassis_only` (matches `class_tables.rs`'s own documented scope: no per-level features, no spell slots). Spells use `full` (the module's documented untruncated corpus text).

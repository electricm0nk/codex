### ⚠ A live corpus-regeneration defect found and NOT triggered against real data

`gen_cache_spell_lane_dump`'s `generate()` calls
`cache_gen::ultimate_equipment::remove_stale_owned_files` per book, which deletes any `.json` file
under that book's `spell/` directory whose `data.key` is not in the CURRENT run's own
`current_keys` set. Running the binary (needed to materialize the two new books) also walks every
OTHER already-covered book in `spell_lane_dump::book_specs()`, including `occult_adventures` and
`ultimate_magic` — and on this run it staged **1,417 + 163 = 1,580 deletions** in those two books'
`spell/` directories.

**Root cause, confirmed by direct count:** `data/corpus/occult_adventures/spell/` held 1,561 files
on disk (145 base declarations from `spell_lane_dump` + ~1,416 `.MOD`-row records written into the
SAME directory by a sibling generator, `cache_gen::spell_mod_access`,
`epic-2-spell-mod-access-no-record-closure_cycle-1_cycle_receipt.md`); `ultimate_magic` held 432
(270 base + 162 MOD rows). `spell_lane_dump`'s `current_keys` set is built ONLY from its own
`SPELL_LIST` table (145 / 270 keys) — it has no knowledge of `spell_mod_access`'s output sharing
the same directory, so `remove_stale_owned_files` correctly-by-its-own-contract, but
catastrophically-in-effect, judged every `.MOD` record "stale" and queued it for deletion.

**Never committed.** Caught via `git status --porcelain -- data/corpus` immediately after the run
(1,582 changes, 1,580 of them `D`), reverted with `git checkout -- data/corpus/occult_adventures
data/corpus/ultimate_magic` before touching anything else. The two new books'
`data/corpus/bestiary{,_4}/spell/` directories (untracked, unaffected by the revert scope) were
already written correctly and are the only corpus change this cycle ships.

**This is a real, pre-existing, unattempted-by-this-cycle defect** — a directory-sharing collision
between `spell_mod_access` and `spell_lane_dump`/`ultimate_equipment::remove_stale_owned_files`
that will fire again, deleting the same ~1,580 real `.MOD` records, the next time anyone re-runs
`gen_cache_spell_lane_dump` for ANY reason (adding an 11th book, a school-mapping fix, anything).
Not fixed here: the safe fix needs `remove_stale_owned_files` to recognize a record it does not own
(e.g. by a shape/kind marker in the JSON, or a per-generator prefix on managed filenames) rather
than deleting everything outside its own `current_keys`, and that is real design work, not a
one-line change, under time pressure I judged too risky to improvise. **Escalated here by name; the
next cycle that touches `spell_lane_dump`, `spell_mod_access`, or
`cache_gen::ultimate_equipment::remove_stale_owned_files` must read this section first and must NOT
re-run `gen_cache_spell_lane_dump` (or any binary that calls `spell_lane_dump::generate`) without
first fixing this, or without first backing up `occult_adventures/spell` and `ultimate_magic/spell`.**

## 2. What "not yet ingested" actually means here — a scope-defining check

Before writing anything, I checked whether the 20 books' `clear` populations really are un-ingested
content, or whether `data/corpus/**` already holds them under a different accounting. It does not:
`data/corpus/bestiary_2/monster_ability/` already ships 493 `.json` records, `bestiary_4/` ships 543
— but those are a **different, already-`done` population** (SD-30/31 monster-ability lane content);
T9's own population filter (`sd32_t9_pi_exposure_audit.py::t9_units`) selects only units whose
`evidence` matches a specific not-ingested pattern per kind, which is disjoint from what's already
shipped. Confirmed by inspection, not assumed.

**The two real ingestion mechanisms in this codebase are different from each other, and neither is a
kind-agnostic "write a corpus-JSON record" pass:**

1. `ingest_spells.rs` (§17's collapsed generic pass) writes a *compiled* `rules_tables::<book>::
   spell_list` Rust module, consumed through `spell_resolver::spell_catalog_rows()`. This is the
   mechanism the brief pointed at.
2. `gen_book_cache.rs` writes `data/corpus/<book>/<kind>/*.json` (Shape B v1) — but only by
   **serializing an already-compiled `rules_tables` module's own accessors**, never by parsing raw
   `.lst` directly. It is the write-side of the pipeline, not a second ingest engine.
3. `enrich_<kind>_raw_tokens.rs` (companion/equipment/monster/monster_ability/spell) only backfills
   the `raw_tokens` field on an **already-shipped** corpus-JSON record; it creates no new records.

So for the five kinds T9 spans other than `spell`, **no generic ingest path exists yet that turns a
raw `.lst` row into a new `data/corpus/**/*.json` record.** Building one from scratch, to this
program's fixture-check/PI-screen/mutation-proof bar, for even one kind, is a full cycle's own scope
— not something this cycle could also complete after re-deriving the disposition and landing the
spell extension below.

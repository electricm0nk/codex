The v0.6 alpha swarm has **three reporting surfaces that must move together**,
and nothing keeps them in sync automatically except this discipline. They
were built at different times for different purposes, and it is easy — this
session proved it, repeatedly — to update one and silently leave the others
stale.

| Surface | What it is | Who reads it |
|---|---|---|
| `docs/release/v0.6/SWARM_REPORT.md` | Two markdown tables: an **Agent Status** table (who's doing what right now) and a separate **per-class detail** table (CRB/APG/ACG breadth). The lead's own working notes, updated most granularly. | Whoever reads the repo directly; also the canonical source the JSON producer parses. |
| `docs/release/v0.6/SWARM_STATUS.md` | A hand-written narrative section, PLUS a separate mechanical `<!-- AUTO-HEARTBEAT-START -->...-END -->` block that a cron script rewrites every 5 minutes (commit hash, timestamps only — never touches the narrative). | The `dashboard-renderer.sh` cron job renders THIS file's narrative into `~/swarm-observer/dashboard.html`/`SWARM_LIVE.txt` every 60s. |
| `~/swarm-observer/PF1e-dashboard.json` | Auto-generated by `pf1e_dashboard_producer.py` (cron, every 5 min) from `SWARM_REPORT.md` + `SWARM_STATUS.md` + `risks-and-open-questions.md`. **Never hand-edit this file** — it will be overwritten on the next tick. | The operator's actual dashboard UI. This is almost certainly what "the dashboard" means when someone says a number looks wrong. |

The auto-heartbeat and the two cron ticks are all mechanical and narrow —
none of them write anything you'd call "progress." If you don't update the
narrative sources yourself, the dashboard freezes at whatever they last said,
while everything genuinely keeps moving underneath it. This happened for real
on 2026-07-27: `SWARM_STATUS.md`'s narrative went ~11.5 hours stale while six
task closures landed, because the lead was diligently updating
`SWARM_REPORT.md` alone and never made the connection that a *second* file
feeds the dashboard.

## When to run this

- **A teammate messages that they're starting a task.** Light touch: update
  `SWARM_REPORT.md`'s Agent Status row for that agent.
- **A teammate messages that they've completed/closed a task.** Full pass,
  below — after you've independently verified their claim, not before.
- **You (the lead) close out a task yourself.**
- **Someone says a dashboard number looks wrong or stale.** Skip to
  "Diagnosing a wrong number," below, before assuming the underlying work
  didn't happen.

## Full pass, on task completion

Do these in order. Skipping the verification step and going straight to
"write it down" is exactly the failure mode this skill exists to prevent —
several "closures" this session turned out to need a follow-up correction
after independent re-verification caught a real miss.

### 1. Verify the claim independently, don't just transcribe it

Sync first (`git fetch origin <branch>`), then re-run what the teammate says
they ran, in an isolated `git worktree` at the actual commit SHA if the main
checkout might have someone else's concurrent edits in it (it usually does,
in a multi-agent swarm — check `git status --porcelain` before trusting a
clean run). At minimum: the full test suite, any class/feature-specific
tests named, both SD-24 coverage audits if class work, clippy. Spot-check at
least one non-trivial factual claim directly against the corpus or code
rather than the chat message describing it. Clean up the worktree
(`git worktree remove <path> --force`) when done.

### 2. Update `SWARM_REPORT.md`'s Agent Status table

One row per agent, near the top of the file. Update the `Status` column
(`in_progress` / `idle` / `completed` framing per-task) and rewrite the
`Detail` cell with what actually landed — commit hash(es), what was verified,
any real finding (a corpus bug, a counting-rule question, a self-caught
mistake). These rows tend to grow very long across a session; when a row
exceeds a few hundred words, compress the older, now-superseded history
into one sentence and lead with the current state — don't just keep
appending forever.

### 3. Update `SWARM_REPORT.md`'s per-class detail table — **separately**

This is the table most likely to be forgotten, because it's a different
table further down the same file, not the one at the top. Find it with:

```bash
grep -n "^| Class | " docs/release/v0.6/SWARM_REPORT.md
```

There are three shapes in this file: the CRB table (`Class | Status |
Race/level support | Landed in`) and the APG/ACG tables (`Class | BAB | Hit
die | Status`, Status is the LAST column in these two). Confirm the row you
edit still has the same column count afterward:

```bash
grep -n "^| Cavalier " docs/release/v0.6/SWARM_REPORT.md | awk -F'|' '{print NF-1}'
```

— compare against another known-good row in the same table. A mismatch means
you accidentally added or removed a `|`-delimited column (this happened for
real this session: pasting a fact like "the Eidolon has full BAB" as its own
`| **full** |` segment instead of folding it into prose).

**The Status cell's wording is load-bearing, not just descriptive.** The
dashboard producer's `extract_open_question()` (in
`~/.hermes/profiles/god-emporer/skills/release-swarm-observer/scripts/observer.py`)
pattern-matches one of these phrasings to pull out a clean blocker summary:

- `"stays Blocked on ..."` / `"still Blocked on ..."` (case-insensitive, tolerates a bold `**Blocked**` right before it)
- `"Only <X> remains ..."`
- `"dispatch-only, Blocked ..."`

If your cell's real blocker doesn't use one of these phrases (e.g. it says
"stays deferred" instead of "stays Blocked on"), the extractor falls back to
raw cell text. As of 2026-07-27 that fallback starts at the row's own
`**Blocked**`/`**Computed**` marker rather than the literal start of the
cell (a real leak — `3/4 | d8 | ` BAB/Hit-die columns bleeding into the
dashboard — was found and fixed this way), but the safest move is still to
use one of the three phrasings above verbatim so extraction is exact, not a
fallback.

For a class that just fully closed (reaches `Computed`), the cell should
read `**Computed**` per the same convention.

### 4. Update `SWARM_STATUS.md`'s hand-written narrative

**Not just the auto-heartbeat block** — that section (between the HTML
comment markers) is cron-owned and only ever carries a commit hash and
timestamps. Find the end of the narrative:

```bash
grep -n "AUTO-HEARTBEAT-START" docs/release/v0.6/SWARM_STATUS.md
```

Insert a fresh `## Agent Status (<date>, ~<time> ET)` section (or a shorter
`**Update (<date>, ~<time> ET): ...**` paragraph appended to the existing
one if it's the same work-window) directly above that marker. Keep it to a
real summary — commit hash, what closed, the headline finding if there was
one — not a full re-derivation of `SWARM_REPORT.md`'s own detail. Point back
to `SWARM_REPORT.md` for the full record rather than duplicating it.

### 5. Refresh the JSON — don't wait on cron

```bash
python3 ~/.hermes/profiles/god-emporer/skills/release-swarm-observer/scripts/pf1e_dashboard_producer.py
```

Run this after every real update rather than leaving it to its 5-minute
cron tick, per standing operator direction (2026-07-27) until the swarm
fully transitions off markdown-sourced rendering. It's cheap and safe to
run — stdlib-only, read-only against the markdown sources, and it always
fully overwrites `PF1e-dashboard.json` from scratch (no partial-write risk).

### 6. Validate the JSON, don't just trust that it ran

```bash
python3 -c "
import json
with open('/home/ubuntu/swarm-observer/PF1e-dashboard.json') as f:
    data = json.load(f)
print('generated_at:', data['generated_at'])   # should be within the last minute
c = next(x for x in data['matrix']['classes'] if x['id'] == '<the class you just touched>')
print(c['state'], '->', c['open_question'])
"
```

Read the actual `open_question` text. Confirm it (a) doesn't start with a
bare `N/d` or `dN | ` fragment (the column-leak bug), (b) doesn't cut off
mid-word or mid-backtick in a confusing way, and (c) actually describes the
*current* blocker, not a pre-closure one. A quick sweep across every class
for the leak pattern:

```bash
python3 -c "
import json, re
with open('/home/ubuntu/swarm-observer/PF1e-dashboard.json') as f:
    data = json.load(f)
print([c['id'] for c in data['matrix']['classes'] if re.match(r'^\d/\d', c.get('open_question',''))])
"
```
should print `[]`.

### 7. Commit and push both markdown files together

One commit for `SWARM_REPORT.md` + `SWARM_STATUS.md` (the JSON is generated,
never committed to git). Update the corresponding `TaskUpdate` status in the
same turn.

## Light touch, on task start

Just step 2 (Agent Status row → `in_progress`, one line on what's starting).
Don't touch the per-class table, `SWARM_STATUS.md`, or the JSON for a bare
task-start — there's nothing new to report yet, and running the full pass
on every start as well as every completion doubles the noise for no signal.

## Diagnosing a wrong number

If someone says a dashboard figure looks stale or wrong, check in this
order before assuming the underlying work is actually stuck:

1. `git log --oneline` on the relevant file/class — did the work actually
   land? (Most of the time: yes, and the reporting pipe is what's broken,
   not the work.)
2. `grep -n "AUTO-HEARTBEAT-START" docs/release/v0.6/SWARM_STATUS.md` and
   read the commit dates on the narrative entries just above it vs. the
   real `git log` — is the narrative behind?
3. `grep -n "^| <ClassName> " docs/release/v0.6/SWARM_REPORT.md` on the
   per-class table specifically — this is the table that's easy to forget
   because the Agent Status table above it looks like "the" status table.
4. Re-run the producer manually and read the JSON directly (step 6 above)
   rather than trusting the rendered HTML, to isolate whether the bug is in
   the markdown source, the producer's parsing, or the render step.

## Gotchas

- **Two tables in `SWARM_REPORT.md`, not one.** The Agent Status table (who's
  doing what) and the per-class detail table (what's true about each class)
  are different sections. The dashboard producer treats the per-class table
  as authoritative for class state — updating only the Agent Status table
  leaves the dashboard showing a class's pre-closure state indefinitely.
- **`SWARM_STATUS.md` has two independent sections that look similar.** The
  auto-heartbeat block (mechanical, cron-owned, HTML-comment-delimited) and
  the hand-written narrative above it. Only the narrative feeds the
  dashboard; the heartbeat block updating every 5 minutes can make the file
  *look* live while the actual content is frozen.
- **A rewritten Status cell needs the exact expected phrasing**, not just
  accurate prose — see step 3. "Stays Blocked on X" extracts cleanly;
  "stays deferred pending X" does not, even though both are equally true
  English.
- **Never hand-edit `PF1e-dashboard.json`.** It's fully regenerated from the
  markdown sources on every run; a manual edit is silently discarded on the
  next tick (cron or manual).
- **`weapon_focus`-shaped misses**: when verifying "all N things are wired,"
  don't check the N things on a remembered list — re-enumerate the full set
  at verification time. A list taken earlier and reused later can go stale
  if the underlying set grew in between (this happened for real: an "8
  orphan producers" inventory from one commit was 1 short by the time a
  later commit claimed to have closed all 8, because a 9th had appeared in
  the interim from concurrent editing).
- **Crossed messages are the norm, not the exception**, in a multi-agent
  swarm. A teammate's message describing what they're about to do may cross
  with your own ruling on the same question, or with another teammate's
  completion report. Always `git fetch` and check `git log`/`git status`
  for ground truth before responding, rather than assuming message order
  reflects real event order.
